4. DOOR-HASH PROVISIONING — SPEC (mechanism only; no hash value is
   recorded in this manifest, by design)
Purpose: Jason set the Speakeasy door password on the VM; the salted
HASH (never the password) rides sync #4 as one-way provisioning so
his starting password simply works on THRONE with no setup step for
him (Rowan's recorded simplification).
How the code already supports it (speakeasy.py, in this payload):
- The door hash is stored in the wing DB table `door`, row id=1,
  column `passphrase_hash`, encoded as
  "pbkdf2-sha256$200000$<salt_hex>$<hash_hex>" (hash_secret()).
- door_configured() and the knock check accept the hash from EITHER
  that DB row OR the environment variable
  LUNA_SPEAKEASY_PASSPHRASE_HASH at runtime ("an encoded hash, never
  a plaintext passphrase").
Verified VM-side at finalization (value NOT read out or printed):
passphrase_hash present=True, length=118, format_ok=True; recovery_hash empty=True.
Install-step mechanism (for the sync #4 installer to execute):
  1. On the VM, read the single encoded passphrase_hash string from
     speakeasy.db's door row. Treat the string as sensitive: do not
     log it, do not commit it to the repo, do not put it in any brief
     that gets pasted anywhere.
  2. On THRONE, apply it by ONE of:
     (a) set LUNA_SPEAKEASY_PASSPHRASE_HASH in the LaunchAgent plist
         EnvironmentVariables (alongside GROQ_API_KEY) and restart
         the service — leaves the Mac wing DB door row empty; OR
     (b) one provisioning insert of the encoded string into the
         THRONE wing DB door row (id=1) before first door use.
     Option (a) is the least invasive and is the recommendation.
  3. Verify with one correct knock (see smoke list) — a successful
     entry files exactly one content-free door_entry crossing.
One-way only: nothing about the wing returns from THRONE to the VM.
